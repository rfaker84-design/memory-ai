# Production Key Rotation Contract

This contract is a release requirement. It does not authorize a production
rotation, read a credential, or provide a way to bypass the production
runtime contract.

## Rules

- Secrets are supplied only through the approved production secret store and
  are never copied into source, release artifacts, process arguments, logs,
  tickets, or chat.
- Every secret has an opaque version identifier, a purpose, an owner, a
  creation time, a planned retirement time, and a rotation audit record.
- A replacement is generated by the account owner or provider, validated in a
  non-production scope, then introduced by an approved production release.
- A secret may be accepted in a bounded dual-validation period only when the
  affected protocol supports it. The old value is revoked after the measured
  maximum validity period plus the documented clock allowance.
- A suspected compromise skips any grace period: revoke or disable the old
  credential, invalidate affected sessions or challenges, and record the
  incident before restoring service.

## Secret classes

| Class | Examples | Rotation behavior |
| --- | --- | --- |
| External provider credential | LLM, Tencent cloud/COS, SMS, WeChat, payment | Provider-side replacement, least-privilege validation, then revoke the old credential. No application dual-read assumption. |
| HMAC identity pepper | phone/request-IP/challenge digest | Requires a versioned database migration and bounded dual-lookup/verification. Do not overwrite in place. |
| Session signing key | `SESSION_SECRET` | New sessions sign only with the active version; verification may accept one prior version until the session TTL plus clock tolerance expires, then revoke it. |
| Internal control token | video review/reconciliation and refund-review tokens | Rotate one control plane at a time with a short overlap, distinct values, caller deployment, audit, and explicit old-token revocation. |
| Short-lived media signing key | staging media signing secret | Introduce a dual verifier only for the maximum signed URL TTL plus clock allowance; new URLs use the active key. |

## Required evidence before a production rotation

1. Owner-approved change record and provider/account authority.
2. Redacted secret-store version identifiers and timestamps, never values.
3. Candidate release SHA and Linux artifact manifest/SBOM/provenance.
4. Staging validation for the affected capability, without real production
   identity, money movement, or provider retries.
5. Dual-validation window, measured expiry/TTL, rollback decision, and
   revocation time.
6. Post-rotation audit proving the old version cannot authenticate or sign,
   with no credential material in logs.

## Current implementation boundary

The current candidate fails closed on missing required runtime values but does
not yet implement versioned dual validation for identity peppers, sessions,
internal control tokens, or signed media URLs. Therefore this document is a
binding implementation and evidence checklist, not proof that a production
rotation is ready. Production remains NO-GO until the corresponding gate is
closed with code, Linux-artifact, and controlled-environment evidence.
